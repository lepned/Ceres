# BT6I8GemmGlu on Hopper (H100): `src/bt6_i8gemm_sm90.cu`

On compute capability 9.0, `launch_i8gemm_glu` runs a Hopper form of the INT8 GEMM with the sigmoid-GLU epilogue. It uses
CUTLASS 3.x warp-specialized persistent kernels: a producer warp issues the TMA loads into a multi-stage shared-memory
pipeline, and consumer warpgroups run wgmma. The epilogue is custom (`GluEpilogue`) and works in registers, on the
accumulators' column pairs:
- scale and bias are loaded once per column pair per tile;
- the codes are built with full-rate float ops (clamp, then `fadd.rm(y, 1.5 * 2^23)`, whose low byte is the code: no
  FRND / F2I);
- a 4 x 4 byte transpose across each quad turns the codes into 16-byte stores.

The epilogue uses the Sm80 visitor's float expressions, so **the codes are bit-identical** to the Sm80 kernel's.
`test/test_glu90.cu` checks this on the real layer weights. It also checks a synthetic +-127 weight case with
accumulators beyond 2^22. Every configuration had 0 mismatches at every M tested.

Nothing else changes: the plugin field, the ONNX and the engine cache stay the same, and the Sm80 kernel stays for every
other GPU.

Switches:
- `BT6_I8GLU_SM90=0` keeps the Sm80 kernel.
- An explicit tile (the `tile` attribute or `BT6_I8GLU_TILE`) also keeps the Sm80 kernel.
- `BT6_I8GLU_SM90_CFG=0..3` forces a Hopper configuration.
- On a launch error the Sm80 kernel runs as the fallback.

## Build

`build_linux.sh` compiles the file separately for `sm_90a` (wgmma needs the arch-specific target) with `-DNDEBUG`, and links
it into the library with `-DBT6_WITH_SM90GLU`. This happens automatically when the `-gencode` list has `compute_90`, which
is true for the default list. `BT6_SM90GLU=0` / `1` forces it off or on. Tested with CUTLASS 4.4 and 4.8.1, nvcc 12.6.
The Windows script is not updated.

**`-DNDEBUG` matters.** Without it, CuTe's device-side asserts leave a function call in the kernel. ptxas then serializes
every wgmma (warning C7510), which cost about 30 % here.

## Results (H100 NVL, TensorRT 10.9, BT6 7M INT8 plugin ONNX, N 2048, K 1024)

Kernel alone, us (median of 40; M = 64 x the Ceres engine batch sizes):

| M | 512 | 2048 | 4096 | 6144 | 8448 | 10752 | 13312 | 14336 |
|---|---|---|---|---|---|---|---|---|
| Sm80 kernel (tile 3) | 14.9 | 21.7 | 37.2 | 52.5 | 68.1 | 90.0 | 106.7 | 114.7 |
| Hopper (default configuration) | 11.9 | 17.0 | 24.9 | 33.0 | 42.3 | 54.0 | 64.0 | 68.5 |
| speedup | 1.25x | 1.28x | 1.49x | 1.59x | 1.61x | 1.67x | 1.67x | 1.67x |

The default is the pingpong 64 x 128 kernel for M <= 1536, and the pingpong 128 x 128 kernel with 2 x 1 clusters above.
In pingpong, one consumer warpgroup's epilogue runs under the other's mainloop. The mainloop alone takes 48 us at
M = 14336 (2.4x the Sm80 kernel). The rest is the epilogue's unavoidable `ex2` + `rcp` per output pair plus its FP32 ops.

Ceres backendbench on the same engine, `BT6_I8GLU_SM90=0` vs default, two runs each:
- average: 8,202 / 8,164 -> 8,540 / 8,536 nps (+4.3 %);
- engine batch 64 / 224: 7.0 / 23.0 -> 6.7 / 22.3 ms.

The kernel was 12.6 % of GPU time in an nsys profile of the INT8 engine.

400-node Ceres searches on 5 positions give the same best moves, PVs and scores. The only differences are in the per-mille
WDL digits, and the Sm80 kernel shows the same differences between two runs of its own (search timing).

## Seen in the same profile, not addressed here

TensorRT inserts about 64K cuTENSOR permutation kernels (3.8 % of GPU time) in the INT8 engine. They come right before the
BT6I8GemmGlu and BT6EgtAttention plugins, after TensorRT's INT8 GEMMs and LayerNorm + quantize. They look like conversions
from TensorRT's vectorized tensor formats to the plugins' row-major (kLINEAR) inputs. The FP16 engine on the GB300 has
none.
