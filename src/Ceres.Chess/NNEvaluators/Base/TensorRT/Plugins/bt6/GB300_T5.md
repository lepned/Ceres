# BT6EgtAttention on the GB300: the t5 kernel (`src/bt6_egt_t5.cu`)

On compute capability 10.3 (GB300 / B300) `launch_egt_attention` runs **t5** instead of v9 for FP16 output. t5 is an EGT2
attention kernel that runs every contraction on the 5th-generation tensor cores (`tcgen05.mma`) and keeps the softmax
operand in Tensor Memory. Every other GPU, and the INT8-output form (`out_int8` = 1), keep v9. Nothing else changes:
the plugin fields, the ONNX, the engine cache, and the other GPUs' code paths are the same. An engine built with
the previous library runs t5 as soon as the new library is loaded.

t5 is release 4 of the lc0ex GB300 attention kernel (`egt_t5.cu`, `t5a.h` and `tmem_ldst.h` from the lczero-triton tcgen05
builder tree, written for lc0ex's BT6 programs). It was ported here with these changes:
- the batch size is a runtime value;
- the plugin's INT32-pair edge bits;
- the constant bias read from the plugin's `[heads][64][64]` table;
- FP16 H export for BT6TripletSite;
- 8 template instantiations (heads per CTA 1 / 2 / 4 / 8 x H export). The file header lists every change.

## Build

`build_linux.sh` compiles `bt6_egt_t5.cu` separately for `sm_103a`, because `tcgen05` needs the arch-specific target.
It then links the result into the library with `-DBT6_WITH_T5`. This happens automatically when the `-gencode` list has
`compute_103`:

    NVCC=/usr/local/cuda-13.2/bin/nvcc TRT_INCLUDE=... CUTLASS_INCLUDE=... ./build_linux.sh "-gencode arch=compute_103,code=sm_103"

`BT6_T5=0` / `1` forces it off or on. It needs nvcc 12.9 or newer. The Windows script is not updated yet; it would take the
same two steps.

Run-time switches:
- `BT6_EGT_T5=0` keeps v9 on the GB300.
- `BT6_EGT_T5_GPC=1|2|4|8` forces the heads per CTA. The default is a wave-count rule on the SM count: 1 / 2 / 4 / 8
  at batch 8 / 16 / 32 / 64, and 4 where 2 x batch CTAs would leave a mostly empty second wave.

## Results (GB300, TensorRT 10.16.1, CUDA 13.2, BT6 7M FP16 plugin ONNX made with `bt6_k1_onnx.py --dynamic --triplet-plugin`)

Kernel alone (`test/test_t5.cu`: real tables of layers 0 and 3, synthetic activations, float64 reference), us per block:

| batch | 8 | 64 | 96 | 224 | 512 |
|---|---|---|---|---|---|
| v9, no H export | 18.9 | 69.8 | 102.3 | 222.9 | 487.1 |
| t5, no H export | 12.1 | 47.2 | 73.8 | 141.1 | 313.5 |
| v9, H export | 19.0 | 71.5 | 110.1 | 229.4 | 500.4 |
| t5, H export | 12.4 | 51.2 | 80.0 | 149.8 | 336.3 |

t5 is more accurate than v9 against the float64 reference:
- output rms error 8.4e-5 vs 1.6e-4 (layer 0);
- H rms error 2.5e-4 vs 5.2e-4 (layer 3).

Ceres backendbench, same engine, `BT6_EGT_T5=0` vs default (two runs each):

| | v9 | t5 |
|---|---|---|
| average over batch 1-2048 | 16,221 / 16,174 nps | 18,560 / 18,541 nps |
| peak | 18.5K | 21.5K |
| engine batch timings 8 / 64 / 224 | 1.3 / 4.2 / 11.6 ms | 1.1 / 3.4 / 9.6 ms |

Root WDL and best move in Ceres (4 positions) are the same as v9's to the permille. Attention went from 42.6 % to 34.2 % of
GPU time (nsys over a backendbench). TensorRT's GEMMs are now the largest share (35.5 %), followed by the fused pointwise
kernels (16.6 %) and the triplet sites (13.0 %).

## Not done / options

- **Packed constant bias.** lc0ex's t5 reads it as one 8-byte load per cell, from a permuted copy
  `[8 groups][64 rows][64 keys][4 heads]`. That copy is the same size as the current table. With the copy, t5 has no
  register spills (the current build spills 4-28 bytes in the GPC 2 / 4 instantiations) and runs 5-10 % faster per block at
  batch 64-512. That is about 1-2.5 % end to end. It would need the copy as an optional 7th input of BT6EgtAttention,
  added in `bt6_k1_onnx.py`. `-DT5_CB_PACK` builds the kernel side of it, used by the test with a permuted table.
- sm_100a (B200) has the same tcgen05 instructions but was not built or run.
- The gates use `tanh.approx` (lc0ex t5's form). It is 6-9 % faster than v9's exact `2 / (1 + exp(-x))` and has the same
  error against float64 to 3 digits. `-DT5_GATE_EXACT` restores the exact form.
